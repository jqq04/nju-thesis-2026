# 答辩PPT纲要

## 1. 项目背景

本文面向广告与商业化业务场景，围绕“内容资产规模大、更新频繁、形态多样、分散沉淀”的现实问题，设计并实现一套内容应用与管理平台。平台以内容全生命周期为主线，将内容管理、内容应用（检索与智能问答）、内容治理（质量闭环）与数据洞察（效果评估与反馈）进行一体化建设。

核心痛点归纳如下：

- 内容分散在不同业务线与系统中，缺乏统一内容模型与统一组织方式，复用成本高。
- 传统内容平台以页面浏览与人工检索为主，难以支撑高频咨询与智能问答入口。
- 随规模扩张出现重复、歧义、覆盖不足等质量问题，依赖人工维护难以长期支撑。
- 缺少“应用效果-问题定位-治理动作-复检回收”的数据闭环，难以持续迭代。

本文建设目标归纳如下：

- 统一管理：建立“空间-应用-类目-标签”的组织体系与多形态内容统一管理。
- 高效应用：在页面化展示与检索基础上，引入基于 RAG 的智能问答能力。
- 质量可控：围绕重复度、歧义度与覆盖度建立治理机制，并落地线上任务闭环。
- 数据驱动：通过事件采集与会话分析支撑评估与反馈，形成持续优化机制。

## 2. 技术综述

本节分为两部分：相关技术一览（表格）与项目中技术应用情况（列表）。

### 2.1 相关技术一览（表格形式）

下表用于在 PPT 中快速交代“平台依赖的关键技术组件及其作用”。

| 技术/组件 | 类别 | 核心作用（面向本项目） |
|---|---|---|
| RocketMQ | 消息队列 | 解耦发布后的异步链路（索引更新、数据回收等），提升吞吐与稳定性 |
| Elasticsearch（Lucene/BM25） | 全文检索 | 关键词检索、结构化过滤、分页与高亮，支撑页面化展示与搜索 |
| Embedding | 表征学习 | 将 Query/切片转为向量，提升语义召回与长尾覆盖 |
| Milvus（ANN/HNSW/IVF等） | 向量数据库 | 语义向量 TopK 检索与过滤，支撑问答证据召回 |
| RAG（检索增强生成） | 应用范式 | “召回-重排-生成”链路，提升问答可用性与可解释性 |
| RRF（Reciprocal Rank Fusion） | 融合重排 | 多通道召回结果融合与重排，提升相关性与稳定性 |
| LLM（大模型服务） | 智能能力 | 问题改写、回答生成、治理判别（重复/歧义/覆盖）与结构化输出 |
| MySQL | 关系型存储 | 组织、内容元数据、权限、审批、治理任务等结构化数据承载 |
| MongoDB | 文档存储 | 承载灵活结构内容（如案例详情等） |
| Redis | 缓存/协调 | 权限结果缓存、热点读缓存、分布式锁等 |
| Hive/数仓 | 离线计算 | 明细与宽表加工，支撑洞察指标与会话分析 |
| SpringBoot | 后端框架 | 按域拆分服务，承载核心业务能力与接口 |
| React | 前端框架 | 管理后台与前台界面实现 |

### 2.2 项目中技术应用情况（列表）

- RocketMQ：发布事件驱动索引更新与统计回收，主链路与异步链路解耦。
- Elasticsearch：承载列表/搜索等高频读场景，利用 Filter 进行状态、类目、标签与权限过滤。
- Milvus + Embedding：承载问答证据切片的向量召回，提高语义匹配与长尾覆盖。
- 多通道召回：ES 全文召回与向量召回并行，提升稳定性与覆盖率。
- RRF 重排：对多通道候选进行融合重排，按倒数排名累加得分并去重输出 TopN 证据。
- LLM 问答：对用户 Query 进行改写，并基于证据集合生成回答，输出携带引用以支持溯源。
- LLM 治理：用于重复/歧义判别与覆盖度判别，输出结构化结果以便落表与任务化。
- 权限体系：RBAC + content_auth 组合，覆盖管理端操作控制与读链路可见性控制。
- 数据洞察：统一事件模型采集 page/search/rag/llm 等链路数据，按 session_id/trace_id 做可追溯分析。

### 4.1 内容组织与应用配置

效果图：

- 应用管理效果图（空间下应用管理、筛选、定位）
  - 文件：../figure/应用管理效果图.png

实现流程（文字说明）：

1. 定义组织边界：以“空间（Space）”作为业务隔离与成员边界，以“应用（App）”作为具体消费场景与配置边界。
2. 定义内容组织：应用内通过“类目（Category）”提供稳定的树状导航，通过“标签（Tag）”提供跨类目的灵活聚合维度。
3. 写入归属字段：每条内容在存储层冗余保存 `space_id`、`app_id`、`category_id` 与 `tag_ids`，保证后续检索、权限与治理都能在统一维度上聚合与过滤。
4. 管理动作入口：管理端提供应用筛选、定位与配置入口，用于维护内容形态开关、类目树、标签体系等场景配置。

关键细节：

- 类目树存储采用路径枚举（path）思想，支持快速子树查询，支撑目录导航与筛选性能。
- 该组织结构贯穿“管理-应用-治理-洞察”四域，是后续所有链路的范围约束基础。

### 4.2 内容生产、审批与发布口径

效果图：

- 文章列表效果图（类目树导航、筛选条件与列表管理）
  - 文件：../figure/文章管理效果图.png
- 文章创编效果图（统一编辑入口与正文编排）
  - 文件：../figure/文章创编效果图.png
- 发布申请效果图（提审/审批入口与状态流转）
  - 文件：../figure/发布申请效果图.png

实现流程（文字说明）：

1. 内容建模：平台以统一内容实体承载公共元数据，不同内容形态（文章/问答/课程/案例）的差异字段落在子表或文档库中，做到“统一口径 + 差异扩展”。
2. 草稿与编辑：内容先进入草稿态，允许迭代编辑；草稿不进入对外可见口径，避免未审内容被检索/问答召回。
3. 提审与审批：内容进入待审批态后冻结对外口径，审批通过后进入已发布态；审批驳回则回到可编辑态并保留意见。
4. 发布事件：内容发布时产生标准化“发布事件”，通过消息队列触发异步链路（全文索引更新、向量切片索引更新、统计回收等），保证主链路低延迟。

关键细节：

- “已发布”是所有对外读链路（门户/搜索/问答）的唯一口径，避免草稿/审批中内容造成口径漂移。
- 发布链路与索引更新解耦，依赖消息队列实现异步一致性与可扩展吞吐。

### 4.3 页面化展示与搜索（门户/列表/筛选）

效果图：

- 典型前台界面效果图（统一搜索入口 + 多类内容聚合展示）
  - 文件：../figure/前台界面效果图.png

实现流程（文字说明）：

1. 列表/搜索走索引：列表页、类目页、标签页、搜索页优先查询 Elasticsearch 索引，避免数据库复杂查询与全表扫描。
2. 过滤前置：将状态（仅已发布）、类目、标签、内容形态、以及权限条件转为 Filter 子句，与倒排索引交集运算得到候选集合，保障分页稳定且无“后置过滤分页空洞”。
3. 详情强一致：列表返回内容 ID 后，再批量回查数据库/缓存获取最新标题、摘要与状态；详情页按内容形态加载对应结构字段或正文，保证最终展示的强一致性。

关键细节：

- “索引圈选 + DB兜底”的读写分离策略：性能由索引保证，一致性由 DB 回查保证。
- 权限参与索引过滤：避免应用层后置过滤导致分页结果变稀疏、用户体验不稳定。

### 4.4 智能问答（RAG：改写、召回、重排、引用）

效果图：

- 智能问答效果图（回答 + 引用溯源呈现）
  - 文件：../figure/智能问答效果图.png

实现流程（文字说明）：

1. 问题改写：对用户原始 Query 做结构化改写（提取对象/场景/诉求），输出更贴近知识标题与正文的检索表达，提升召回稳定性。
2. 多通道召回：并行执行两路召回：
   1. 全文通道（ES）：适合命中专有名词、错误码、规则编号等显式关键词，并天然支持过滤条件。
   2. 向量通道（Milvus）：适合语义改写与口语化表达，提升长尾覆盖，同样支持基于元数据的过滤。
3. 候选融合去重：将两路候选按“切片/内容”的唯一标识去重，避免重复证据污染上下文窗口。
4. RRF 重排：对每路候选按名次分配倒数排名分值并累加，得到融合分数后排序输出 TopN 证据集合。
5. 证据组织与生成：将 TopN 证据（含 Title/Text/Key 等标准字段）注入提示词，生成回答并返回“可映射引用”，保证回答可追溯到具体内容与切片。

关键细节（需要在 PPT 中讲清楚）：

- RRF 的工程口径：对每个通道内排名为 `rank` 的候选赋分 `1 / (rank + k)`，本文实现采用平滑常数 `k=60`；同一候选在多通道的分值相加作为最终融合分数。
- 关键参数含义：
  - `TopK`：单通道召回候选上限，用于控制延迟与后续开销。
  - `MinScore`：低相关候选过滤阈值，用于提升精度与可解释性。
  - `TopN`：最终证据数量，受上下文窗口与引用展示约束。
- 输出的引用必须能映射到 `content` 与 `slice`：这是后续治理与问题定位的入口条件。

### 4.5 内容治理闭环（发现、任务化、处理、复检回收）

效果图：

- 治理任务线上化效果图（治理工单、分发、状态跟踪）
  - 文件：../figure/治理任务线上化效果图.png

实现流程（文字说明）：

1. 问题发现：围绕重复度、歧义度、覆盖度三类质量问题产出“问题候选”。
2. 重复/歧义检测两阶段：
   1. 候选召回：先用向量检索缩小比对范围（从全量两两比对降到局部邻域）。
   2. 精判别：再用大模型对候选对做深语义比对，判定“重复”或“歧义（口径冲突/表述矛盾）”，并输出结构化依据。
3. 覆盖度检测机制：以真实会话日志为输入，对未命中或低质量命中的 Query 做语义聚类形成问题簇；对代表性 Query 判别覆盖情况，若未覆盖则生成“缺知识”任务。
4. 任务线上化：将结果转为“主任务（Batch）-子任务（Item）”两层工单：
   1. 主任务记录一次治理的范围与版本（空间、时间窗口、算法版本等）。
   2. 子任务对应可执行实体（重复/歧义的内容对；覆盖度的问题簇）。
5. 处理与回收：人工处理后子任务先进入“已处理待复检”；系统按日巡检复检，仅当问题消除后才自动关闭任务，确保治理有效。

关键细节：

- 幂等创建：任务生成以“任务类型 + 实体标识”为唯一约束，避免重复生成导致治理噪声。
- 状态口径：主任务（新建/运行中/完成），子任务（待处理/处理中/已处理/已关闭），保证治理可追踪、可统计。
- 治理动作要与内容发布链路打通：处理产生的内容修订/下线，必须经发布事件驱动索引更新，保证结果在检索/问答侧可见。

### 4.6 数据洞察（会话分析与链路追踪）

效果图：

- 会话分析效果图（指标汇总 + 问题簇下钻）
  - 文件：../figure/数据洞察——会话分析效果图.png

实现流程（文字说明）：

1. 统一事件模型：页面化链路采集曝光/点击/搜索等事件；问答链路采集召回、重排、生成、转人工等事件，均携带统一公共维度字段。
2. 双标识追踪：
   1. `session_id`：组织多轮交互与漏斗分析。
   2. `trace_id`：贯穿单轮问答的召回-重排-生成关键节点，用于端到端还原证据与决策链路。
3. 数仓加工：事件进入数仓侧加工为明细表与指标宽表，洞察模块提供只读查询接口与权限控制。
4. 结果下钻：洞察侧支持“宏观指标趋势 -> 聚类级主题 -> 会话明细 -> 引用证据”的分析路径，用于定位高频问题与薄弱点，并反哺覆盖度治理与策略优化。

关键细节：

- 事件字段需同时覆盖“范围维度（space/app）”与“内容维度（content/slice）”，否则无法做到从效果到内容的可回溯闭环。
- 采集接入层对 `(trace_id, event_name)` 做幂等去重，避免指标膨胀。
